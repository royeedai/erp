# OA、ERP、财务与应收应付前端基座方案

**我的建议是采用 React + TypeScript + Ant Design，先交付一套能生成普通业务页面的工程模板，再用付款申请验证它的边界。** 基础控件直接使用组件库。项目自己维护的内容集中在组织参照、金额展示、单据操作区、明细错误定位、导入结果等业务约定。首期不建设通用低代码平台，也不把电子表格、流程设计器和甘特图列入自研组件清单。

我会用三种页面验收这套基座：

1. **项目岗位**验证普通开发者能否按规范生成 CRUD，也验证“已引用不能删除”“项目经理岗位唯一”等约束能否呈现清楚。
2. **资产卡片**验证多分区详情、按类别变化的字段、关联档案、字段权限和历史记录能否复用。
3. **付款申请**验证最重要的业务边界。参考产品里，保存就可能预占资金计划，审批人可以改金额，一行申请可以分次生成付款，结算结果还要回写来源。如果模板把这些都处理成一个“保存成功”，界面再整齐也不能交付。依据见 `pm.txt p23`、`asset.txt p64–66`、`treasury.txt p65–66`。

以下以**中文桌面 Web、前后端分离、没有必须继承的前端技术栈**为设计假设。文档页码均指正文的 `===== pN =====` 标记。三份材料足以判断页面形态，但没有给出本项目的首期范围、实际交易量，也不能替代完整的 OA、总账和应收应付需求。

## 一、文档里真正反复出现的页面和交互

为判断复用优先级，我对 `pm.txt p22–77`、`asset.txt p41–172`、`treasury.txt p55–267` 共 401 页做了正文关键词复核。按“同页同组只计一次”，含“审批”的有 **224 页**，含“查询或台账”的有 **187 页**，含“参照、拉单或回写”的有 **125 页**，含“批量”的有 **68 页**，含“导入或导出”的有 **62 页**，含“对账或核销”的有 **16 页**。不同组可以重叠。下表的频度指**预计开发时复用的程度**，用户实际每天使用多少次，需要上线数据或岗位访谈验证。

| 页面或交互 | 复用频度 | 正文证据 | 前端最难的点 |
|---|---|---|---|
| 档案、字典、树形分类 | 高，最适合首批生成 | 项目岗位支持父分类继承、唯一经理岗位及引用保护；合同类型分集团和组织；竞争对手档案支持树形结构。`pm.txt p23–24、p27` | 同名档案属于不同组织；停用后历史单据仍需显示原值；“不可删”要能解释原因 |
| 查询列表、业务台账、穿透详情 | 极高，几乎每个模块需要 | 项目台账支持输出、打印，项目看板可穿透原单；资产台账可按位置、部门等维度汇总；资金计划可按主体、年月、币种、版本查询。`pm.txt p25`、`asset.txt p70`、`treasury.txt p247` | 用户从汇总点进原单再返回时，组织、期间、筛选和行位置都要保住；全量合计必须与查询口径一致 |
| 主子表及多表体单据 | 极高，投入重点 | 收款合同有四种价格约定，清单与协议可并存，并做价税分离；付款申请一笔可有多种款项，审批中还能修改申请金额。`pm.txt p40–41`、`treasury.txt p65` | 表头变化影响哪些行、哪些金额能改、错误在第几行；审批状态和合同履行状态必须分开 |
| 参照选单、按行生成、上下游联查 | 极高，应做公共交互 | 进度款可抵预付款，且受已完成报量约束；付款申请可引用进度款、支付证书等来源；同一申请可多次生成付款，合单还受组织、币种、供应商等条件限制。`pm.txt p53–54`、`treasury.txt p65–66` | 保留来源**行**、可用余额、本次使用量和未用量。两人同时拉同一余额时，由服务端决定哪次成功 |
| 对象卡片、业务历史、版本对比 | 高 | 资产卡片包含财务信息、技术参数、父子资产、零部件及生命周期附卡；技术参数随资产类别变化。收款合同可对比历史版本，资产变动台账展示变动前后内容。`asset.txt p64–66、p73`、`pm.txt p41` | 当前值、制单时快照和异动记录容易混淆；大量附卡应按需加载，并沿用各自权限 |
| 我的待办、审批详情、按节点编辑 | 极高，OA 与财务共用 | 项目建议书有唯一审批通过约束；付款计划可逐行改核定金额；资金计划的指标审批可改数并看单元格历史，改数保存后仍需审批。`pm.txt p26、p50`、`treasury.txt p247` | 审批涉及字段编辑权、差异、意见和任务并发。一个全局 `readonly` 或“同意/拒绝”弹窗覆盖不了 |
| 跨组织协同、任务下发与差异处置 | 中高，资产和财资集中 | 所有权调拨和使用权调拨影响不同，调出会协同生成对方调入单；盘点分粗定范围、分派、实盘、盘盈盘亏及差异调整；到账通知可发布给成员单位认领。`asset.txt p73、p76–77`、`treasury.txt p87` | 调出方完成不等于调入方完成；两方可见内容不同。盘点还要区分未盘、已盘相符、已盘有差异 |
| 双边匹配、核销、对账 | 全局中频，相关岗位核心 | 发票与业务单据支持多对多核销、手输核销额、联查记录；银行对账支持自动和手工，合并支付时标识码可能无法精确匹配；总账与业务账的账户范围可能不同。`pm.txt p56`、`treasury.txt p68、p86–87` | 双方筛选、部分匹配、差额、已占用金额要同屏；先说明核对范围，再判断是否对平 |
| 计划编制、预算矩阵、指标审核 | 页面数中低，单页复杂度极高 | 项目预算按项目、CBS、核算要素逐级汇总，可在保存、提交或审批时预警或强控；资金计划支持上下级差额、浮动行、指标改数，部分直接调整在 Excel 客户端完成。`pm.txt p36`、`treasury.txt p246–248` | 单元格有维度、版本、编辑权和计算来源。需要先验证真实工作簿是否必须保留 |
| 批量作业、票据指令、结果跟踪 | 高，适合共用任务与结果页 | 待建资产支持按列批改、批量建卡；资产可按查询条件批量打印；票据背书支持批量发送指令、作废，联查票据台账、审批流和凭证。`asset.txt p64、p66`、`treasury.txt p155–156` | 按行呈现成功、失败、处理中和待确认；银行处理成功、业务审批通过、会计入账是不同事实 |
| 分析看板、图表入账表、专业图形 | 看板中频，专业编辑器低频 | 项目利润的取数来源随系统对接情况变化；资产分布可从地图下钻台账再到卡片；项目排程支持四种依赖、关键路径、工作日历与拖动连线。`pm.txt p25、p69`、`asset.txt p70` | 看板难在指标口径与穿透一致；可编辑排程涉及计算模型，应单独选成熟产品 |

功能清单也支持这个划分。`pm.txt p15` 同时列出档案、台账、登记和立项，`asset.txt p31` 把待建卡、卡片维护、批量打印和台账分成不同入口，`treasury.txt p42` 则区分付款申请、资金付款、协同确认和期末处理。**导航可以分模块，模板应按用户正在完成的工作来分。**

## 二、技术选型

“AI 易落地”采用可验收的定义：生成结果使用官方 API、只依赖仓库里看得见的示例，下一位开发者能在普通 IDE 中改字段、定位报错、运行测试。下表的否决理由指本项目不把备选作为默认的原因。

| 分项 | 明确推荐 | 备选 | 不作为默认的理由 / 切换条件 |
|---|---|---|---|
| 框架 | **React + TypeScript strict，客户端 SPA**。按业务域拆路由，模块内直接写组件 | Vue + TypeScript | 两者都能做。无存量约束时选 React，表单、表格、流程查看沿用同一套示例。若长期维护者已有成熟 Vue 工程和发布链，整体切 Vue 比让团队维护双栈更合理。[React 官方版本页](https://react.dev/versions) |
| 组件库 | **Ant Design**。Form、Table、TreeSelect、Drawer、Upload、Descriptions、Timeline 直接使用，主题走 ConfigProvider | Element Plus，配 Vue | Element Plus 能覆盖同类控件，但需要连框架一起切换。项目内只保留一套表单校验、弹层和键盘行为。[Ant Design Table](https://ant.design/components/table/) · [Element Plus Table](https://element-plus.org/en-US/component/table.html) |
| Pro 层 | **首期用仓库内的页面模板组合 Ant Design，默认零 Pro 运行时依赖**。查询、分页、错误和缓存只有一个负责人 | Ant Design ProComponents，优先试 ProTable / ProForm | ProTable 对标准查询页有价值，但其请求、表单和列配置容易与项目 Schema、Query 缓存重复。只有试点证明确实减少维护量，且目标版本兼容时才纳入。可单独用 ProComponents，无须为它引入整套后台脚手架。[官方仓库](https://github.com/ant-design/pro-components) |
| 表格 | **Ant Design Table** 做服务端分页、固定列、汇总；中小型可编辑明细用 Table + Form，使用稳定行 ID | AG Grid，按需求选 Community / Enterprise | 只有真实样例要求大批量粘贴、范围选择、复杂分组或高密度连续编辑时才切专业网格。先核对所需功能属于哪个版本，避免做到一半才发现采购依赖。[Ant Design Table](https://ant.design/components/table/) · [AG Grid 版本对照](https://www.ag-grid.com/react-data-grid/community-vs-enterprise/) |
| 状态 | **TanStack Query 管服务端数据，Ant Form 管编辑值，URL 管查询，React state/context 管短期界面状态** | Redux Toolkit + RTK Query | 项目已有 Redux 基础设施时可选；新项目用两套全局状态保存同一张单据，容易在审批后显示旧值。[TanStack Query](https://tanstack.com/query/latest/docs/framework/react/overview) |
| 请求与契约 | **OpenAPI + openapi-typescript + openapi-fetch**，统一鉴权、取消、错误映射、追踪号；Query 调用该客户端 | Axios 实例 + 生成的 DTO | 已有统一 Axios 拦截器可保留。单靠手写 Axios 接口会让 AI 猜字段、金额类型和分页协议。[OpenAPI TypeScript](https://openapi-ts.dev/introduction) |
| 路由与权限 | **React Router Data Mode**；路由登记资源码，服务端返回数据范围、字段能力和当前可执行动作 | TanStack Router + 同一后端权限契约 | 强类型搜索参数很有价值，但首期路由和筛选可由现有 schema 校验。无论哪种路由，读取、导出和写操作均由服务端逐次授权。[React Router](https://reactrouter.com/start/data/routing) |
| 图表 | **Apache ECharts**，按需引入柱、线、堆叠等图型，给出同口径明细入口 | Ant Design Charts | 管理看板可用备选快速搭建；本项目还涉及分层统计、计划曲线和细粒度联动，直接用 ECharts 能减少封装层排查。[ECharts 官方手册](https://echarts.apache.org/handbook/en/how-to/chart-types/bar/basic-bar/) |
| 工作流与流程图 | **接后端既有工作流任务 API**。办理页用 Timeline 展示实际历史；若后端提供带布局的 BPMN XML，再接 bpmn-js Viewer 高亮实例节点 | 嵌入既有 OA 或流程引擎自带的办理页、设计器 | 既有平台能满足统一登录、组织切换、字段权限和回跳时，嵌入成本可能更低。首期自行画节点和连线会把流程语义也揽进前端。[bpmn-js](https://bpmn.io/toolkit/bpmn-js/) · [许可证](https://bpmn.io/license/) |
| 打印 | **正式单据用独立 HTML 打印模板，服务端 Chromium/Playwright 按单据快照生成 PDF**；前端预览同一 PDF | 浏览器打印 CSS + 原生打印 | 临时清单适合原生打印；正式单据的中文字体、分页、重复表头、打印版本需要统一控制。预印纸、标签机另用真机验收。[Playwright PDF API](https://playwright.dev/docs/api/class-page#page-pdf) |
| 导入导出 | **服务端模板与文件任务**。前端负责上传、预检、错误定位、进度和下载。若服务端为 Java，推荐 Apache POI，量大时采用流式处理 | 浏览器端 SheetJS，限小文件预览或简单导出 | 全量台账涉及查询快照、字段权和内存。浏览器方案适合低敏、小批量，不承担正式入账。后端语言未定，无需专为表格另建 Java 服务。[Apache POI](https://poi.apache.org/components/spreadsheet/) |
| 构建 | **Vite + pnpm + 锁文件**，CI 固定 Node 和包管理器版本，按业务路由拆包 | 团队既有 webpack 工程 | 存量插件或指定浏览器依赖可构成保留理由；新工程重建一套手工 webpack 配置收益有限。[Vite](https://vite.dev/guide/) |
| 测试 | **Vitest + Testing Library + Playwright**。分别覆盖字段规则、用户交互、跨页业务链；接口反例使用 MSW 或测试服务 | Jest + Testing Library + Cypress | 现有 Cypress 资产充足时保留。新仓库统一 Vite 与测试配置，浏览器测试也能复用打印基础设施。[Vitest](https://vitest.dev/guide/) · [Playwright](https://playwright.dev/docs/api/class-page) |
| 代码规范 | **TypeScript strict + ESLint/typescript-eslint + Prettier**，业务目录使用受限导入规则；格式与类型检查分开 | Biome + `tsc --noEmit` | 备选适合更看重单工具速度的团队；本项目需要检查类型误用、异步调用和模块边界，先用容易逐条解释的规则集。[typescript-eslint](https://typescript-eslint.io/getting-started/typed-linting/) |

**版本与费用核实。** 本次在线读取的官方页面显示 React 文档版本 **19.3**、Ant Design 组件页 **6.7.2**、TanStack Query 的 React 文档为 **v5**。这些是各自页面标示的版本，整组依赖的 peer 兼容、内网浏览器和现有插件组合**未核实**，不能直接当安装清单。开工时应在同一个试点工程里验证并锁定精确版本。Ant Design 仓库采用 MIT；AG Grid Community 为 MIT，Enterprise 需商业许可，面向外部客户的应用需按使用场景询价，**本项目成交价未核实**；bpmn-js 的许可要求保留可见水印。ProComponents 对目标组合的兼容性、长期维护承诺及企业支持费用**未核实**。[React](https://react.dev/versions) · [Ant Design](https://ant.design/components/table/) · [Ant Design 许可证](https://github.com/ant-design/ant-design/blob/master/LICENSE) · [TanStack Query](https://tanstack.com/query/latest/docs/framework/react/overview) · [AG Grid 许可](https://www.ag-grid.com/react-data-grid/community-vs-enterprise/) · [AG Grid 报价条件](https://www.ag-grid.com/license-pricing/) · [bpmn.io 许可](https://bpmn.io/license/)

## 三、视觉与字段规范

选**浅色、高信息密度的业务工作台**。左侧是业务导航，顶部始终看得见当前组织，页面主体留给查询、表格和单据。列表页打开就能查数。单据页最醒目的区域固定放**单号、业务状态、金额及币种、当前可办动作**。同一位置在合同、付款申请和资产调拨中承担同一职责；没有金额的单据换成调出/调入组织等关键识别信息。

### 建议直接固化的 token

下列名称是项目语义 token，颜色、字号和控件尺寸映射到 Ant Design 主题，布局尺寸输出为 CSS 变量。单位除颜色和字重外为 px。

| 用途 | 名称与值 |
|---|---|
| 品牌与交互 | `primary #175CD3`，`primaryHover #124CA9`，`selectedBg #EAF2FF`，`focusRing #175CD3`，焦点环 `2`，外偏移 `2` |
| 背景与边界 | `canvas #F4F6F8`，`surface #FFFFFF`，`tableHead #F0F3F7`，`rowHover #F5F8FC`，`border #D5DCE5`，`inputBorder #8793A3` |
| 文字 | `text #182230`，`textSecondary #475467`，`textMuted #586679`；正文 `14/22`，表格 `14/20`，辅助 `12/18`，区块标题 `16/24`，页标题 `20/28`，核心金额 `24/32`；常规字重 `400`，标题与合计 `600` |
| 状态前景／底色 | 草稿 `#475467 / #F2F4F7`，处理中 `#175CD3 / #EAF2FF`，已完成 `#176B45 / #EAF7EF`，需关注 `#854A00 / #FFF4D6`，失败或阻断 `#B42318 / #FDECEA`。每个状态同时显示文字；“已审批”“已结算”使用完整状态名 |

### 字段展示契约

| 字段 | 强制规则 |
|---|---|
| 金额与数量 | 金额右对齐、千分位、同列同精度。单币种在列头标“申请金额（CNY）”，多币种逐行显示 ISO 币种。零显示 `0.00`（按币种精度），缺值显示 `—`，负数保留负号。数量、单价、税率、汇率分别定义精度；金额传十进制字符串，本地预览使用十进制运算，最终金额及舍入取服务端结果 |
| 合计 | 明示“本页合计”“查询结果合计”或“已选合计”。不同币种分组合计；折算合计同时给本位币、汇率日期和口径。税前、税额、含税分列；不能从屏幕已舍入的行金额反推记账金额 |
| 日期与期间 | 业务日期 `YYYY-MM-DD`，会计期间 `YYYY-MM`，操作时间 `YYYY-MM-DD HH:mm:ss`。纯日期按字符串传递，审计时间保存带时区的时间戳，跨地区页面明确显示时区 |
| 编码与账户 | 编码、票号、账号均按字符串处理，保留前导零。单号可复制、可联查；宽度不足时保留识别所需的首尾段。银行账号默认脱敏，复制、导出与明文查看分别受权 |
| 参照与历史 | 选择器显示“编码 + 名称 + 必要的组织”，提交稳定 ID。历史单据显示制单时名称，停用项标“已停用”；新建时过滤不可选项。布尔值区分“是 / 否 / 未设置” |

## 四、可直接写入验收用例的 UX 规则

| 场景 | 统一行为 |
|---|---|
| 列表与查询 | 默认显示 3–5 个常用条件，其余折叠。输入期间不反复刷新全表，Enter 或“查询”应用条件；重置回到当前组织的默认范围。服务端筛选、排序、分页，默认每页 50 条，可选 20/50/100。排序增加稳定的 ID 次序。组织、期间等非敏感条件进入 URL，账号等敏感条件不入 URL |
| 表格与参照 | 单号在左、金额右对齐；表头固定，常用业务动作最多直接露出两个。双击可以加速，必须另有可见入口。大档案用可检索、分页的参照窗口；变更组织或供应商可能使已选行失效时，先列出受影响行再处理 |
| 简单表单 | 少量独立字段可用抽屉；需要跨区核对、附件或多行编辑时用独立路由。必填、单位、默认值来源可见。失焦校验格式，提交校验整单并定位首错；保留用户输入，服务端错误映射到具体字段，未知错误显示追踪号 |
| 主子表 | 固定顺序为表头、明细、分币种合计、附件、操作区。行用稳定 ID，支持新增、复制、移除及键盘移动。复制时清除行 ID、来源占用、审批和结算结果。跨页或虚拟化时保留未保存行；错误摘要可跳到“付款明细第 8 行 · 本次申请金额” |
| 保存与提交 | 动词写清副作用。“暂存草稿”必须对应真实无占用草稿能力；若保存会预占计划，按钮或邻近说明明确“保存后预占 CNY 10,000.00”。提交前展示阻断项和可继续的预警。写请求带版本与幂等标识；超时先按操作号查结果，付款和发指令不可自动重发 |
| 详情与联查 | 顶部固定身份信息及独立状态，正文分基本信息、明细、来源/下游、审批、变更记录。按需加载各区。由台账进详情后返回，恢复筛选、分页和滚动锚点。联查无权的关联单据时按授权展示可见摘要或受限提示 |
| 审批 | 待办打开**对应任务和单据版本**。只开放本节点授权字段，改金额要并列显示原值、核定值、差额。驳回说明去向和原因；撤回、弃审、作废独立命名。已被同事处理时刷新任务并保留可复制的意见草稿。付款审批通过后显示真实后续状态 |
| 批量操作 | 明确“当前页 50 条”“已选 8 条”或“本次筛选全部 2,341 条”。跨页全选由服务端保存筛选快照及排除项。执行前显示可执行数、跳过数、分币种金额；结果逐行可查。只对明确失败且可安全重试的行提供重试 |
| 删除及纠正 | 草稿删除提示单号、数量和影响。已引用档案显示阻断原因及可访问的引用入口。已生效财务单据按后端允许动作走作废、红冲或更正，保留原记录。不可逆或涉及支付的确认框写具体动作，普通保存免二次确认 |
| 导入 | 下载带版本模板 → 上传 → 预检 → 查看新增/更新/覆盖与错误行 → 确认执行 → 下载结果。错误给原文件行号、列名、原因。**整表覆盖**显示将替换的原行数；变更态不可导入时禁用并说明。期初增量导入与合同清单全量覆盖必须有不同测试。`pm.txt p23、p41` |
| 导出与打印 | 提供已选或查询结果两种范围；下载前标明组织、期间、列集和脱敏口径。大任务可离页，在任务中心查看进度；下载时复核权限。打印按业务模板重复列头、分组小计、页码，预览显示单据版本。资产批量打印直接按筛选任务执行 |
| 空、错、慢、无权 | 首次无数据且有权限时给“新建”；筛选为空给“清除条件”；首载用骨架，刷新保留旧表并标记更新中。查询失败保留条件和重试。403 显示所需权限或可联系角色，清退不可见旧数据。保存冲突显示“你的值 / 最新值”，可重载后重新应用修改 |
| 快捷键与焦点 | Tab 顺序跟随视觉顺序；编辑明细时 Enter 确认当前单元格，Esc 退出该次编辑，弹层关闭后焦点回到触发点。Ctrl/Cmd+S 仅在存在安全暂存动作时启用。审批通过、删除、付款、发指令均无单键触发 |
| 多页签与未保存 | 用户可复制真实 URL。若启用应用内页签，同组织同单据同模式复用，默认最多 8 个；达到上限让用户选择关闭项。脏页显示圆点，关闭页签、返回、切组织均检查未保存修改。浏览器关闭使用原生离开提醒；财务明细默认不写入浏览器持久存储 |

**对账页单独验收。** 左侧显示账簿记录，右侧显示银行记录，底部持续显示双方已选笔数、金额、差额及币种。自动匹配要能解释依据；人工多对多核销要能录本次分配额。数据范围不同先提示范围差异，合并支付不能唯一匹配时进入待人工确认。一次核销成功后，两侧余额和历史记录从服务端一起刷新。这里值得写专用页面。`pm.txt p56`、`treasury.txt p68、p86–87`。

## 五、怎样让任何开发者或 AI 按规范生成 CRUD

### 1. 固定模板和扩展边界

| 交付级别 | 页面模板 | 生成到什么程度 |
|---|---|---|
| A · 可直接生成 | 档案列表 + 抽屉表单、树 + 列表、只读台账、简单申请 + 详情 | 字段、筛选、分页、详情、操作入口、空错态和基础测试全部生成。能否删除、能否提交由接口返回 |
| B · 生成骨架，填写业务扩展 | 主子表单据、资产卡片、选来源行、审批办理、导入任务、汇总下钻 | 生成区块、路由、数据绑定和错误定位；开发者实现有类型的取数、联动、校验与领域命令 |
| C · 专页开发 | 多对多核销、银行对账、计划矩阵、专业排程、移动扫码盘点 | 共用导航、权限、字段格式、任务结果和设计 token。交互编排独立实现；网格、排程、扫码优先接已验证的产品或设备 SDK |

**边界判据**：只改字段、顺序、显隐、参照来源、操作标识，就进配置。需要记住多步临时状态、协调两个数据集、分配金额、处理外部回执，直接写业务代码。一个页面例外不升级全局 Schema；至少两个真实页面出现相同语义，再提取公共能力。

### 2. 把接口契约和页面 Schema 分开

OpenAPI 描述传输字段、类型、分页、错误和命令。页面 Schema 描述用户看见什么、如何查询、按哪种模板呈现。以下是**建议协议示意**，其中操作名须与实际 OpenAPI 对齐。

```ts
export const projectRolePage = {
  schemaVersion: 1,
  resource: "project.role",
  template: "tree-list-form",
  rowKey: "id",
  scope: ["orgId", "projectCategoryId"],
  operations: {
    list: "listProjectRoles",
    create: "createProjectRole",
    update: "updateProjectRole",
    remove: "deleteProjectRole",
  },
  fields: [
    { key: "code", label: "岗位编码", kind: "code", required: true },
    { key: "name", label: "岗位名称", kind: "text", required: true },
    { key: "enabled", label: "启用状态", kind: "boolean" },
  ],
  columns: ["code", "name", "enabled"],
  filters: ["name", "enabled"],
  actions: [{ id: "remove", capability: "delete", confirm: "record" }],
} satisfies ResourcePageSpec<ProjectRole>
```

再约定四类接口行为，模板才真的可用：

- **查询与参照**返回稳定 ID、总数或游标、明确口径的合计；缓存键含租户、组织、资源和查询条件。身份或数据范围切换后清理旧缓存。
- **详情与能力**返回 `version`、业务状态、审批状态，以及 `allowedActions`、必要的禁用原因和字段读写能力。敏感字段由后端裁剪；导出、附件、联查同样鉴权。
- **业务命令**分开定义保存、提交、作废、生成下游等操作，携带预期版本及幂等键。主子表原子保存；资金占用、部分生成、税额舍入、状态转换由后端事务裁决。
- **错误与异步任务**返回稳定错误码、字段路径或明细行 ID、业务提示、追踪号；长任务返回任务 ID，支持查状态及逐行结果。页面不解析中文报错来推断业务状态。

### 3. 让规范进入仓库和 CI

```text
src/app/                    路由、组织上下文、权限、应用布局
src/api/generated/          OpenAPI 生成类型，禁止手改
src/shared/ui/              金额、参照、单据头、操作区、结果反馈
src/shared/patterns/        台账、树表、主子表、审批、导入任务模板
src/features/<域>/<资源>/   page.schema.ts、页面、命令、扩展、测试
src/theme/                  语义 token、组件映射、打印样式
generators/                 Plop 模板、Schema 校验、生成器版本
examples/                   项目岗位、资产卡片、付款申请三个可运行样例
docs/standards/             字段字典、状态矩阵、接口与交互约定
AGENTS.md                   生成步骤、允许依赖、示例入口、验收命令
```

建议提供 `pnpm gen:resource --spec <文件>`、`pnpm check:schema`、`pnpm check` 三个入口。生成器先验证资源码、字段、字典、operationId 和模板名，再生成路由、页面、用例。生成目录允许重建，人工扩展放独立文件；重复执行应得到相同输出，遇到人工文件冲突则报告路径。Plop 已能承担文件模板与批量生成。[Plop 官方文档](https://plopjs.com/documentation/)

`AGENTS.md` 要短到开发者也愿意读：先选最接近的样例，再绑定已有接口；禁止猜枚举、端点和财务公式；新增依赖或模板能力要说明现有方案缺什么。**CI 执行真正的约束**：

- 类型检查、Schema 校验、路由和资源码唯一性、OpenAPI 重新生成无漂移。限制业务页直接发裸请求、导入未批准的第二套 UI 库、绕过公共金额格式化。
- 模板测试包含正常、空、403、字段校验失败、版本冲突、重复点击、批量部分失败。金额样例包含零、负数、精度不同的币种和含税尾差。
- 浏览器测试走真实入口，至少覆盖“查询 → 编辑 → 返回保留条件”“申请 → 审批改额 → 部分生成 → 查余额”“跨组织后旧数据不可见”。金额与权限类断言不能只用截图代替。
- **生成能力验收**：让未参与搭建的人和 AI 分别根据同一字段清单生成一个新档案页。两份都应直接运行、通过同一测试，无需改公共模板。记录额外手工修改了什么，据此修正规范。

## 六、风险、最大不确定性与必须先确认的问题

| 优先级 | 要向朋友或业务负责人确认的问题 | 会改变的决策 |
|---|---|---|
| 1 | **首期由哪些岗位完成哪三条端到端业务？** 请给脱敏的真实单据、Excel、打印件各一份，以及每条业务一个失败案例。OA 是普通申请审批，还是包含公文、用印、移动待办？应收应付做到台账，还是做到核销、制证、结账？ | 这是最大不确定性。参考产品的广度远大于一个项目的合理首期，答案决定模板顺序及可承诺的交付范围 |
| 2 | 后端和现有系统分别负责哪些动作？保存是否预占、谁能审批改额、付款超时如何查结果、部分生成如何回写、谁是金额和单据状态的权威来源？ | **最大实施风险**。缺少这些契约，前端只能演示页面，无法验收真实资金链 |
| 3 | 有几个租户、集团、法人及财务组织？代办、跨组织、制单与复核如何分权？哪些金额、账号、附件可看、可导出、可打印？ | 决定数据模型、缓存隔离、字段裁剪和审计。后补会影响几乎所有页面 |
| 4 | 单据明细行数、最大台账、同时在线人数、粘贴规模、导出体量分别是多少？是否必须复现 Excel 的公式、浮动行和既有工作簿？ | 决定普通表格能否胜任、是否采购专业网格、哪些操作必须改异步。应取得典型值和峰值各一份 |
| 5 | 现有 OA/SSO/流程引擎是什么？是否要求业务人员在浏览器设计流程？银企直联、签名、会计平台由谁接？ | 决定集成或采购范围，以及审批页能否直接嵌入现有平台 |
| 6 | 由谁长期维护，团队熟 React 还是 Vue？交付给内部使用还是对客户部署？允许哪些商业组件、预算多少、是否要求纯内网和指定浏览器？ | 可推翻默认框架，直接影响商业许可、字体、依赖镜像和部署选型 |
| 7 | 是否有移动审批、PDA/RFID、离线盘点、预印纸、标签机或指定打印精度？哪些必须在首期用真机交付？ | 这些是独立终端及外设需求。桌面响应式和 A4 PDF 无法证明它们可用。`asset.txt p76、p169` |

我对**普通 CRUD 和台账基座**的判断最有把握。对**专业网格是否值得买、是否要做移动端、付款链能自动化到哪一步**，现有材料不足以定案。最有效的澄清材料是一份真实大明细、一张退回或部分付款的单据，以及对应岗位现场操作的过程。

## 七、分阶段产物与验收

| 阶段 | 交付产物 | 通过标准 |
|---|---|---|
| 0 · 定首期边界 | 三条业务链、角色/组织矩阵、脱敏样单、状态与金额口径、目标设备和数据量、技术决策记录 | 业务负责人能用样单讲完正常与异常路径；前后端能逐项说清谁校验、谁记账、失败后如何恢复；专业网格和工作流有明确试验范围 |
| 1 · 验证工程基座 | 可运行应用、主题 token、路由/鉴权、API 客户端、错误映射、CI、项目岗位样例 | 目标浏览器从登录到查询、编辑、返回全程可用；跨组织隔离、引用阻删、键盘操作和 403 均通过；依赖锁定后 CI 可重复构建 |
| 2 · 验证三张代表页 | 项目岗位完整 CRUD、资产卡片详情/编辑、付款申请主子表及审批联调 | 用真实接口走通卡片分类切换和权限变化；付款申请覆盖保存预占、审批改额、部分生成、冲突与重复提交。未进入项目范围的场景由双方明确删去，模拟接口结果单独标明 |
| 3 · 固化生成能力 | Schema、生成器、模板目录、AI 规则、字段字典、标准用例和迁移说明 | 由新人和 AI 各生成一个未见过的真实档案页；无需改基座，CI 全绿，二次生成不覆盖人工扩展。评审记录生成耗时和人工修正项 |
| 4 · 攻克专业场景 | 对账工作台、导入任务、正式打印样张；按范围试验计划矩阵、专业网格或移动盘点 | 多对多核销及余额正确；错误文件能定位到行列；大导出可离页；打印经业务对照签样。用阶段 0 的峰值数据在目标设备测试，普通表格未达标再决定采购 |
| 5 · 试点与移交 | 按一个组织或岗位试点、监控与追踪、回退方案、维护手册、样例库 | 关键业务无重复执行、无越权、金额与后端对平；操作失败可凭追踪号定位。第二位维护者独立新增、测试、发布一个资源页面后再扩大推广 |

**首期最值得承诺的交付，是“下一位开发者能生成一张合格的档案页，业务人员能核清一笔付款从申请到结算的每个金额”。** 前者证明开发规范可复制，后者证明这套基座承载得住企业业务。
